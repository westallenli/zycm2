# 智援参谋智能体整体升级 Implementation Plan

> **For Codex / 新对话执行者：** 按本计划逐项执行，一轮只推进一个有界任务；可使用本机已有 executing-plans 技能，不依赖未安装的 superpowers 技能。用户明确要求开始后才实施，本轮仅编写计划。
>
> **Goal:** 在原软件基础上完成全地图沙盘、可操作SOP、全部已确认业务与统一UI的较大迭代，保留应保留的旧能力并完成可追溯验收。
>
> **Architecture:** 先盘点旧能力和统一领域契约；复用通过核验的Python领域/审计/存储能力，重整页面交互与应用服务。外部数据、模型工具、模拟与真实接入经明确适配层，页面不能直接绕过权限修改正式状态。
>
> **Tech Stack:** 已有Python、标准库HTTP服务端页面、JavaScript地图交互、SQLite/JSON及规则配置是核查基线；新前端框架或存储替换不预先指定，P00/P01/P02记录选择及成本，避免无业务理由整体换栈。

起草：2026-09-23；完成交接：2026-09-24；版本 V1.0。配套[完整总规格](../../整体升级开发总规格_V2.0.md)与[开工交接](../交接_整体升级_开始开发.md)。
本计划替代功能清单中的旧 I00-I14 执行顺序；需求编号与F编号不变。

## 1. 目标、事实与不确定性

已确认：大版本迭代而非强制从零重写；旧功能保留完善、四模块全部纳入；完整地图+浮层+一目了然流程；既定人工权限及模拟/真实边界继续有效。新的界面只是本次重点，不是全部范围。
已知事实：旧代码仓库 HEAD 在本轮为 260c31a，git diff --stat 无已跟踪改动；仅未跟踪 impl/snapshots/fire-002.db。新需求目录非Git仓库。本轮未运行功能回归。
未知：旧功能逐项实测结果、具体设备与真实接口、专业阈值和实际屏幕条件。已有82个功能目录、268条来源，不等于旧软件完整性已经验收。
不承诺：一次零返工、无专业人员独立安全灭火、未接入设备已真实可用、固定模拟算法具有真实预测准确性。

建议由新对话从旧仓库HEAD创建隔离工作树，保留用户原仓库与未跟踪快照。不要整体复制私人数据、环境密钥、缓存或自动把原快照当演示数据；不覆盖/删除旧仓库。

## 3. 实施顺序与控制点

P00 基线盘点 → P01 数据/权限/历史契约 → P02 统一UI与地图浮层 → P03 check-in → P04 SOP → P05 战术地图 → P06 任务闭环 → P07 对讲/定位 → P08 人员物资 → P09 智能分析问答 → P10 动态模拟与数据源 → P11 复盘回放 → P12 根因整改经验 → P13 报告问询对接 → P14 全链联调 → P15 验收交付。
P16 是后续部署/跨事件分析边界，不要求首期实现其中未授权项目。

控制点：
- G0：P00盘点形成旧能力去向表，不能漏掉后台能力。
- G1：P01共同对象/权限/版本时间契约明确，P02整体交互可审阅；先展示关键布局与主要操作，再批量铺完整页面。没有新业务决策待确认时继续独立基础工作，不把用户沉默当新的布局批准。
- G2：P03-P10贯通现场业务，未接真接口的来源明确模拟；不能用页面硬编码替代后端流程。
- G3：P11-P13完整复盘及报告联通本事件数据，全部更正范围生效。
- G4：P14-P15验收证据完整，专业待审/真接入限制单列，不把“测试通过”当可生产指挥。

每个P阶段可分为多个小任务；每次只选择一个目标，例如“补到不重复计入随队物资”。每个任务步骤：
1. 读取该需求/现有代码与工作区diff，列受影响对象和调用链。
2. 对业务/状态/权限变更先写能揭示差异的行为检查或测试，并确认在旧行为下能暴露问题；纯样式采用实际浏览器检查，不写镜像测试。
3. 实现最小可用变更，数据与权限走统一服务。
4. 跑相关测试与页面操作；失败定位修复，不跳过或伪造结果。
5. 更新需求映射和WORKLOG，记录完成/未完/验证/风险；按仓库约定形成可回滚提交，未经请求不推远端或部署。

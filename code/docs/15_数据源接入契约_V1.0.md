# 熊猫智脑 数据源接入契约 V1.0

> 文档定位：本文件是**外部观测数据进入熊猫智脑工作区的唯一对接口径**。
> 将来与指挥现场系统（无人机、气象、水文等）对接开发网关软件时，以此契约为准；
> 网关只需按本契约产出观测数据，系统侧下游链路（摄取→桥接→阈值推导→共享态势）无需改动。
>
> 核对基线：`impl/panda_brain/ingestion.py`、`intake_bridge.py`、`scenario_driver.py`（P11-T2 逐项与代码核对，每节标注锚点函数）。若代码与本文件冲突，以代码为准并回改本文。

---

## 一、四条铁律（不可协商）

| # | 铁律 | 含义 | 锚点 |
|---|------|------|------|
| 1 | **单位白名单，拒绝即报** | 单位不在白名单的观测一律拒收，绝不静默换算 | `ingestion.UNIT_WHITELIST` |
| 2 | **摄取≠验证** | 仪器读数入账只能是 OBSERVED 态势；VERIFIED 只能来自授权核实通道的人工判断 | `intake_bridge` 模块 docstring、`IntakeBridge.bridge_pending` |
| 3 | **传感器永不触碰 VERIFIED** | 传感观测既不产生 VERIFIED，也不把已 VERIFIED 的 claim 打回；陈旧读数不得覆盖后来的现场核实 | `scenario_driver._apply_thresholds` 守卫分支 |
| 4 | **幂等** | 同一内容重复投递零副作用：摄取层按内容哈希去重，桥接层按证据存在性跳过 | `ObservationStore.import_json`、`bridge_pending` 的 skipped 分支 |

另有一条空态纪律：空观测库的状态是显式的 `bootstrap_required`，系统**没有**任何样例数据生成入口——缺数据就是缺数据（`ObservationStore.status`）。

## 二、单条观测的字段契约

网关提交的是观测条目列表（JSON 数组）。每个条目：

| 字段 | 类型 | 要求 | 校验失败报错（原文） | 锚点 |
|------|------|------|----------------------|------|
| `site_id` | str | 非空，去首尾空白后参与一切标识 | `missing site_id` | `validate_observations` |
| `metric` | str | 必须在下方指标-单位绑定表内 | `unknown metric '…'; known metrics: […]` | 同上 |
| `unit` | str | 必须**恰好等于**该 metric 绑定的单位；且在单位白名单内 | `metric '…' requires unit '…', got '…'` / `unit '…' outside whitelist […]` | 同上 |
| `value` | number | 可转 float 且有限（NaN/inf 拒收） | `value … is not a finite number` | 同上 |
| `observed_at` | str | ISO 8601 且**必须携带显式 UTC 偏移**（如 `+08:00`）；不带时区的裸时间拒收，系统不猜时区 | `Timezone-naive timestamp rejected: … Supply an explicit UTC offset.` | `normalize_to_shanghai` |

**注意：`source` 不是条目内字段。** 数据来源以批量导入参数传入（`import_json(items, source=...)`），同一批次的全部条目共用一个来源名。来源名同时决定信任级别（见第四节）。

### 2.1 指标-单位绑定表（`ingestion.METRIC_UNITS`，当前全量）

| metric | 要求 unit | 物理含义 |
|--------|-----------|----------|
| `water_level_m` | `m` | 水位 |
| `discharge_m3_s` | `m3/s` | 流量 |
| `precipitation_mm` | `mm` | 降水 |
| `wind_speed_m_s` | `m/s` | 风速 |
| `temperature_c` | `C` | 温度 |
| `humidity_pct` | `%` | 湿度 |
| `alert_level` | `dimensionless` | 预警等级 |

单位白名单（`UNIT_WHITELIST`）：`m`、`mm`、`m3/s`、`m/s`、`C`、`%`、`dimensionless`。新增指标须先扩此绑定表并过评审，网关不得自行发明指标名。

### 2.2 时间戳归一

`normalize_to_shanghai(raw)`：解析 ISO 时间 → 减去原偏移得 UTC → 加 8 小时，返回 Asia/Shanghai 墙上时间的 ISO 字符串（中国自 1991 年起无夏令时，固定 UTC+8）。后续一切排序、哈希均用归一后的时间。

## 三、标识与幂等机制

| 对象 | 生成规则 | 锚点 |
|------|----------|------|
| 观测 ID `observation_id` | `SHA256("site_id\|metric\|repr(value)\|unit\|observed_at归一后\|source")` 十六进制；任一成分不同即不同观测 | `validate_observations` 的 `digest_basis` |
| 证据 ID `evidence_id` | `"obs-" + observation_id[:32]` | `IntakeBridge.evidence_id_for` |
| claim 主语 `subject` | `"<site_id>:<metric>"`（域标签格式，供检索匹配） | `IntakeBridge.claim_subject_for` |

幂等的两层保证：

1. **摄取层**：同 `observation_id` 再次导入 → 计入重复清单、跳过插入，账面零变化（`ObservationStore.import_json`）；
2. **桥接层**：证据 ID 已存在于工作区 → 跳过桥接，把摄取层的内容哈希幂等上传到 claim 层（`bridge_pending` skipped 分支）。桥接是从工作区状态派生的，可重启、可重放。

## 四、信任级别与验证边界

| 来源情形 | 入账信任级别 | 锚点 |
|----------|--------------|------|
| 来源在授权名单内（`authorized_sources`，如演练中的 `sensor-feed`、`recon-alpha`） | `AUTHORIZED` | `IntakeBridge.trust_level_for` |
| 来源不在名单内 | `PENDING_VERIFICATION` | 同上 |

- 桥接产生的证据快照不可变，含内容哈希（`Evidence.create`）；桥接置信度固定 `0.9`（`_INTAKE_CONFIDENCE`），语义为"仪器如实上报"。
- 桥接产物一律 `OBSERVED`。claim 升到 `VERIFIED` 的唯一通路是**带 AUTHORIZED 证据的授权核实判定**，该门禁在工作区内部（政策规则 `verified-basis-for-l3` 及相关核实流程），桥接层无权也无力绕过。
- `SourceTrustLevel` 全集：`authorized` / `pending_verification` / `untrusted`；摄取桥只产生前两种，`untrusted` 留给其他显式降级场景，不由数据通道自动赋予。

## 五、阈值推导规则（观测如何变成领域条件 claim)

规则全部在配置文件中声明（当前 `impl/config/forest_fire_thresholds.yaml`），改规则不改代码。严格加载器拒绝未知顶层键（`schema_version`、`thresholds` 之外即报错，`load_threshold_rules`）。

每条规则字段：

| 字段 | 必填 | 说明 |
|------|------|------|
| `subject` | 是 | 目标 claim 主语，**必须带域前缀**（含 `:`），如 `weather:wind` |
| `metric` | 是 | 匹配的观测指标名 |
| `site` | 否 | 限定站点；省略则该指标任意站点的新读数都驱动此规则 |
| `op` | 是 | `>=` / `<=` / `>` / `<` 四选一，越界报 `Unknown operator` |
| `value` | 是 | 阈值数值 |
| `met_value` | 是 | 越阈时目标 claim 取的值（如 `high`） |
| `not_met_value` | 是 | 未越阈时的取值（如 `low`） |

推导语义（`ScenarioDriver._apply_thresholds`，顺序即实现顺序）：

1. 每个 `(site_id, metric)` 组合取**最新**一条观测（按归一后时间）；
2. 最新读数越阈与否决定目标值；同站多站点规则由 `site` 过滤；
3. **守卫一**：目标 claim 已是 `VERIFIED` → 直接跳过（铁律 3）;
4. **守卫二**：目标值与现状相同 → 不产生事件（确定性优先于消息量）;
5. **守卫三**：最新观测的证据尚未桥接进工作区 → 跳过（推导必须有据可依）;
6. 通过则写入/更新 claim：值=`met_value`/`not_met_value`，状态恒 `OBSERVED`，置信度 `0.9`，证据指向最新观测的 `evidence_id`。

`ScenarioDriver.step()` 的返回始终显式：空库返回 `bootstrap_required`；就绪则返回 `bridged` 与 `claims_updated` 清单。编排提问（`orchestrate_question`）是可选触发，数据面从不自动发起参谋流程。

## 六、对接方式约定（本阶段决策记录）

P11 决策：真实数据源对接推迟到具体软件阶段（现场无人机/气象/水文系统的形态确定后再建通道）。本阶段**不建传输通道，只固化本契约**。届时：

- 网关侧只需产出符合第二~四节的观测条目 JSON 数组，并声明真实的来源名；
- 授权来源名单由系统侧评审后配置，网关不得自称 AUTHORIZED（信任级别是系统侧按名单判定的，不是网关声明的）;
- 新增指标类型走"扩 `METRIC_UNITS` 绑定表 + 评审"路径；
- 文件投递式接入（收件箱目录）与 HTTP 轮询槽位的具体形态届时另行拆解设计。

## 七、符合本契约的样例

```json
[
  {
    "site_id": "sx-hanjiang-001",
    "metric": "water_level_m",
    "unit": "m",
    "value": 2.8,
    "observed_at": "2026-08-22T09:30:00+08:00"
  },
  {
    "site_id": "sx-weather-01",
    "metric": "wind_speed_m_s",
    "unit": "m/s",
    "value": 11.4,
    "observed_at": "2026-08-22T01:30:00+00:00"
  }
]
```

说明：两条观测若以 `source="sensor-feed"` 导入且站点/指标/数值/时间完全相同，则无论投递多少次，账面上永远只有各一条记录（第三节幂等机制）。第二条故意用 UTC 零时区写法——归一后与北京时间为同一时刻。

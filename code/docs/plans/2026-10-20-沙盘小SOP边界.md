# 沙盘小 SOP 边界（用户确认）

起草：2026-10-20。本条是**边界约定**，不是开发计划；后续每轮改动都按这里的清单核对。

## 1. 层级划分（最重要，别混）

| | 归谁 | 内容 |
|---|---|---|
| **九步走** | **整个系统** | 早期处置／态势研判／力量调用／任务部署／组织扑救／清理看守／应急救援／信息发布／验收交接 |
| **七环节小 SOP** | **沙盘** | 侦察核实／态势研判／确定方案／编组下达／接收执行／跟踪调整／核验后续 |

两者**不冲突**：沙盘做七环节；九步走归系统层，沙盘上只留一个**链接入口**过去。

用户原话：「九步走是整个系统的，不是给沙盘的。我们现在做的是沙盘的小 SOP。这跟九步走不冲突，但是九步走的功能是能链接过来的。」

## 2. 底部"9 项工作导航"要去掉

**这是位置错误，不是功能错误。**
把全系统的九步导航塞在沙盘底部，等于让沙盘承担系统层导航，而且跟七环节抢同一条位置。

| 对象 | 处理 |
|---|---|
| 沙盘底部九项横条 | **去掉** |
| 沙盘"当前建议"（按九项算"第 N 项"） | **去掉** |
| 沙盘隐藏的九项详情区（9 段 `guide()` 内容） | **不再渲染** |
| 九步走功能本身 | **保留**，留在全系统入口，一个字不删 |
| 沙盘上的九步走 | 只在七环节条尾留**一个链接** `/workflow/guide` |

`render_shell_navigation(show_workflow=False)` 时：九项导航、"当前建议"、隐藏详情三者全部不渲染，
连那 9 次片段解析与 9 次 `guide()` 也一并省掉——沙盘不再为九步走重复计算。

## 3. 沙盘其他功能一律不动

以下全部保留原位，只加不删：

- 左侧工具坞：5 个图标 + "更多"菜单
- 浮窗：关注事项、方案与行动、智能参谋、统一助手、侦察、图例图层、地图工具、当前对象、信息全景、待核对追问、标绘作业、测算、影像、指令草稿、问询
- 地图：图层开关、状态过滤、方案叠加、推演、态势复核、标绘工具
- **气象卡（右上角）**：温度／风向／风速／湿度四格，可收起为"气象"小按钮，画图时自动收起并自动还原；**只读本事件已有观测，不联网不编造，无数据显示"气象资料未接入"**。位置在 `sand-command.css:2`（`right:58px; top:14px`），数据在 `sand_command.weather_snapshot()`
- 右侧：参谋对话、方案栏
- 顶部：事件标题、数据截至、刷新状态
- 左下"当前建议"（`.sop-next`）：**沙盘不再渲染**。它按九项算"第 N 项·某项"，属于九步走内容（2026-10-20 用户指出"沙盘里又出现九步走"后撤掉）
- **"灭火指挥待办"（`command-sop.js`）**：**保留**，是沙盘上唯一的待办列表；七环节的待办行取自同一份数据

## 3.1 与气象卡的位置冲突（已处理）

待办抽屉原计划 `top:24px right:24px`，会压住右上角气象卡（z-index 930 对 35）。处理原则：
**不收起、不搬走、不隐藏气象**，改为让位置。
- 桌面：抽屉 `top:206px`，整体落在气象卡下方
- 手机：屏幕不够，允许抽屉压过气象；关掉抽屉气象原样回来（它自带收起/展开）
- 兜底：`.sand-weather` 与 `.sand-weather-reopen` 的 z-index 提到 940，保证任何时候不被待办压住

## 4. 本轮新增（只留两块）

1. **底部七环节胶囊**：一排 38px 小胶囊，点开看该环节的待办
2. **环节面板**：点胶囊后在右侧显示这一步要做什么、有哪些待办、下一步去哪

## 4.2 两个视图，两种人（2026-10-20 用户澄清）

沙盘上要同时服务两种人，**不是二选一**：

| | 左侧「指挥待办」 | 底部七环节 → 环节内容 |
|---|---|---|
| 给谁 | **会指挥的人** | **不会指挥的人** |
| 回答什么 | 现在最急的是哪几条 | 我现在该干什么 |
| 呈现 | 完整队列、优先级、状态、责任人、可点办理 | **最多 3 条**，每条一句人话 + **一个「去办理」按钮**；其余收成"还有 N 项 · 看左侧指挥待办" |
| 术语 | 优先判断／尽快核对／待安排 | **一个术语都不用** |
| 数据 | `command_sop.queue()` | **同一份**，只做裁剪 |

原则：**一份数据、两种读法**。两份数据永远会出现"哪边更靠谱"的困惑，已按此统一。

## 4.4 刷新周期（2026-10-20 用户确认：3 秒太紧张，改 3 分钟）

统一的业务口径：**数据更新周期默认 3 分钟，可选 3／5／10／30／60**（`scenario_runtime.REFRESH_MINUTES`）。
页面轮询改为与之一致，不再每 3 秒空转：

| 位置 | 原 | 现 |
|---|---|---|
| 沙盘运行状态 | 3 秒 | **3 分钟** |
| 资料核对 | 3 秒 | **3 分钟** |
| 现场联动 | 3 秒 | **3 分钟** |
| 指挥助手 | 3 秒 | **3 分钟** |
| 九步走状态 | 3 秒 | **3 分钟** |

- 提交动作后**仍立即刷新**，不必等下一轮
- **演示批次：60 秒 → 30 秒**（`map-demo.js` 的 `STEP_MS`）。演示的标注变化由浏览器本地引擎推进，
  不经过轮询，所以改这一处最直接：六批约 3 分钟走完，画面每 30 秒变一次
- 演示模式仍按批次本地推进，不受轮询周期影响
- 效益：沙盘无效请求从每分钟约 80 次降到 1~2 次；九步走不再每 3 秒重算九个环节

## 4.5 已知空缺

- 第 2 环节（态势研判）在指挥待办里没有独立阶段 → 显示"暂无待办"
- 第 5 环节（接收执行）只在"未接收／待接收"时才有对应行
- 七环节状态只由该队列推导：priority=1 的环节标"卡住"，排第一那条所在环节标"当前"，其余"未办"；**不推断"已完成"**

## 5. 交互口径

- 减字：默认每条待办只显示 标题 + 按钮 + 谁办；"为什么／怎么算完／接什么／点什么"收进折叠的「依据」
- 按钮就是按钮：按优先级给动词（立即处置／去补齐／去核对／看进展），不写"点击查看更多"
- 七环节格子**点它不标记完成**：打开页面、点过步骤都不算完成，只有业务记录推进才算
- 待办排序只影响先后，**不放宽任何权限或门禁**
- "已下达"不等于"已执行"：第 5 环节状态只从既有接收／回执记录读，不自行推断

## 6. 视觉一致性

沙盘作用域用亮蓝紫 `#3669de` + 玻璃面 + 12px 圆角（不是五页那套 `#245B78` 白卡）。
复用既有类：`.sop-next`、`.sop-path`、`.lz-btn`；只新增 `.field-*`。
样式：`static/field-sop.css`；交互：`static/field-sop.js`；渲染：`panda_brain/field_sop_view.py`；算分：`panda_brain/field_sop.py`。

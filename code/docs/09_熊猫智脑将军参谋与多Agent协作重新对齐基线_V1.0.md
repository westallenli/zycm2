## 1. 重新对齐后的产品定位

熊猫智脑不是一个接到目标后自己拆解、自己判断、自己执行、自己宣布完成的自动驾驶系统。

熊猫智脑是你的**参谋部**：

- 你是将军，负责方向、优先级、取舍和最终决断；
- 熊猫智脑负责与你共同观察、收集信息、分析形势、提出方案和汇报结果；
- 它可以有自己的判断，而且要把判断依据摆出来；
- 你也有自己的判断，可以采纳、否决、修正，或直接提出新的方案；
- 它收集的信息你必须能看见、能使用、能质疑；
- 它只有在你形成明确决断并下达命令后，才执行会改变外部现实的动作；
- 执行中发生命令之外的新情况，它必须回来报告，不能自行改变战略方向。

核心闭环调整为：

```text
共同观察
  → 多角度分析
  → 共享材料与分歧
  → 共同讨论
  → 将军决断
  → 命令确认
  → 参谋执行
  → 过程汇报
  → 结果验证
  → 共同复盘
```

这和旧项目 README 中的：

```text
Think → Decide → Act → Observe → Think again
```

不是同一个产品关系。旧循环可以保留为“命令执行后的工程闭环”，不能再作为熊猫智脑的完整产品闭环。

## 2. 对原有设计的重新解释

### 2.1 原 `03` 核心对象与安全模型：保留，但降低产品中心位置

以下对象仍然是必要的工程对象：

- Goal：目标；
- Task / Phase：目标下的工作组织；
- State：当前已知事实、推断、未知和约束；
- Observation / Evidence：观察和证据；
- Decision：决策材料和候选方案；
- Action Contract：结构化动作协议；
- Approval：对具体行动的授权记录；
- Execution / Result / Verification：执行、结果和独立验证。

需要补充的边界：

- `Decision` 首先表示参谋形成的决策材料和候选方案，不表示已经由系统拍板；
- 必须增加 `GeneralDecision`，表示你的最终选择、修改、否决、暂缓或自提方案；
- 必须增加 `ExecutionOrder`，表示基于你的决断形成的明确执行命令；
- `Action Contract` 不能直接从参谋输出进入执行器，必须经过：

```text
AdvisorProposal
  → GeneralDecision
  → ExecutionOrder
  → Policy / Approval
  → Executor
```

### 2.2 原 `04` 执行层：保留，但执行对象改为将军命令

原文关于执行层解耦、OpenClaw 可替换、Policy、Approval、三层结果和验证的设计继续有效。

但是执行层的触发语义必须改为：

```text
参谋提议 ≠ 将军决断
将军决断 ≠ 无边界授权
将军命令 + Policy通过 + 参数确定 = 才能执行
```

Policy 是系统安全底线，不是参谋或其他 Agent 的业务决策权。即使你选择了某个方案，系统仍然可以因为 L5、越权、参数不完整、命令过期或无法回滚而拒绝执行，并把原因报告给你。

### 2.3 原 `06` SimulatorExecutor：保留，重新定义用途

SimulatorExecutor 不再主要验证“AI 能不能自己循环完成目标”，而是验证：

- 多个参谋 Agent 能否围绕同一份世界状态协作；
- 各 Agent 能否留下独立情报、判断和证据来源；
- 你否决推荐后，流程是否真的按你的选择改变；
- 没有你的命令时，任何 Agent 是否都无法触发外部动作；
- 执行结果不确定时，是否先观察和验证而不是重复提交；
- 失败发生后，是否回到共同讨论而不是 Agent 之间自行争执并继续执行。

## 3. 将军、参谋长和专业 Agent 的关系

### 3.1 将军：唯一的业务决断者

你拥有：

- 目标和优先级定义权；
- 关键约束补充权；
- 情报取舍和方向修正权；
- 方案采纳、否决、修改和自提权；
- 执行命令下达、暂停、取消和改令权；
- 对结果是否接受的最终判断权。

系统不能把你的角色降级成“点批准按钮的人”。你应该能在信息收集和方案形成过程中就参与、质疑和改变方向。

### 3.2 参谋长：协作编排者，不是第二个将军

建议设置一个 `ChiefAdvisor` 或 `StaffCoordinator` 作为参谋长，职责是：

- 把你的目标转成当前议题和待解决问题；
- 判断需要哪些专业 Agent 参与；
- 分配调查任务和信息范围；
- 汇总各 Agent 的材料；
- 标注一致意见、分歧意见和证据冲突；
- 形成给你看的综合判断和方案集；
- 组织讨论节点，等待你的决断；
- 将你的决断转成明确执行命令；
- 监督执行汇报、验证和复盘。

参谋长不能：

- 代替你选择业务方案；
- 因为多数 Agent 同意就自动执行；
- 把自己的综合结论写成事实；
- 修改你的命令而不报告；
- 让专业 Agent 直接调用高风险执行器。

### 3.3 专业 Agent：参谋部中的分工岗位

专业 Agent 可以拥有独立分析视角，但没有最终决断权。建议岗位如下：

| Agent | 主要职责 | 典型输出 | 默认权限 |
|---|---|---|---|
| `ResearchAgent` 情报参谋 | 收集和整理指定来源信息 | 原始情报、来源、时间、可靠性、缺口 | 只读信息源 |
| `AnalysisAgent` 形势参谋 | 基于共享材料识别事实、假设、趋势和风险 | 判断、依据、置信度、未知项 | 只读共享工作区 |
| `OptionAgent` 方案参谋 | 提出可行路径并比较成本、收益、风险和可逆性 | 方案集、对比、推荐 | 只读共享材料，写方案草案 |
| `RedTeamAgent` 反方参谋 | 主动寻找漏洞、反例、失败路径和遗漏约束 | 反对意见、风险清单、需要补证的结论 | 只读，不得改写原始情报 |
| `FeasibilityAgent` 可行性参谋 | 评估方案是否可执行、缺什么资源或权限 | 可行性评估、前置条件、估算 | 只读，必要时申请模拟检查 |
| `VerificationAgent` 核验参谋 | 独立检查执行结果和业务条件 | Observation、Evidence、VerificationResult | 只读结果和证据，不能自报完成 |
| `MemoryAgent` 记录参谋 | 整理决策历史、复盘经验和将军确认内容 | 记忆候选、复盘草案、来源 | 不能单方面升级长期规则 |
| `ExecutionAgent` 执行参谋 | 按明确命令调用执行器并汇报 | 执行进度、结果、异常、证据 | 无命令不得执行 |

第一阶段不需要全部实现。先做 `ResearchAgent + AnalysisAgent + RedTeamAgent + ChiefAdvisor` 的离线协作即可。

## 4. 多 Agent 是否值得采用

### 4.1 结论：可以采用，但要采用“受编排的参谋部”

多 Agent 对熊猫智脑有价值，原因不是“Agent 越多越聪明”，而是不同岗位可以提供不同视角：

- 情报 Agent 负责广度和来源整理；
- 分析 Agent 负责把材料变成判断；
- 反方 Agent 专门寻找分析中的漏洞；
- 方案 Agent 负责把选择空间摆出来；
- 核验 Agent 防止执行者自己宣布成功。

这正好符合你说的关系：你在考虑，参谋也在考虑；参谋可以提出不同意见，但最后由你决断。

### 4.2 多 Agent 不能解决的问题

多 Agent 不会自动带来正确答案，反而会引入新的风险：

- Agent 互相复制错误信息，形成虚假共识；
- 多数票压过你的现场判断；
- 多个 Agent 重复搜索，成本和噪声增加；
- Agent 之间互相调用，出现循环和责任不清；
- 反方 Agent 为了表现不同而制造无意义反对；
- 汇总 Agent 把推断压缩成没有来源的结论；
- 某个 Agent 越权调用执行器；
- 多个 Agent 同时修改共享状态，造成版本覆盖；
- 复杂编排让系统慢于你自己判断。

所以多 Agent 的设计原则不是“让它们自由讨论”，而是：

> **角色分工、共享证据、保留分歧、单一编排、将军决断、执行隔离。**

### 4.3 不建议的方案

以下方案不纳入熊猫智脑正式架构：

1. 多个 Agent 自由聊天，最后由一个 Agent 猜多数意见；
2. 多个 Agent 投票后自动决定方案；
3. 每个 Agent 都拥有独立工具和执行权限；
4. 一个 Agent 生成任务，另一个 Agent 自动执行，不经过将军决断；
5. 为了“多 Agent”而把同一个模型复制五份；
6. 先上分布式消息队列、复杂自治循环，再验证协同逻辑。

## 5. 推荐的多 Agent 协作拓扑

```text
                         将军（你）
                   目标 / 补充 / 质疑 / 决断
                              │
                              ▼
                    ┌─────────────────┐
                    │  ChiefAdvisor   │
                    │  参谋长/编排器    │
                    └───────┬─────────┘
                            │
          ┌─────────────────┼─────────────────┐
          ▼                 ▼                 ▼
   ResearchAgent      AnalysisAgent      RedTeamAgent
    情报参谋             形势参谋            反方参谋
          │                 │                 │
          └────────────┬────┴────┬────────────┘
                       ▼         ▼
                 Shared Workspace
                 共享态势与证据台
                       │
                       ▼
                 OptionAgent
                 方案参谋
                       │
                       ▼
           参谋方案 + 分歧 + 风险 + 推荐
                       │
                       ▼
                    将军决断
                       │
                       ▼
              命令确认 + Policy校验
                       │
             ┌─────────┴─────────┐
             ▼                   ▼
       ExecutionAgent       HumanExecutor
       执行参谋               人工执行
             │
             ▼
       VerificationAgent
       独立核验
             │
             ▼
       ChiefAdvisor 汇报复盘
```

关键约束：

- 专业 Agent 只能向共享工作区写自己的产物；
- 只有参谋长负责把产物组合成“待将军讨论”的材料；
- 只有将军决断才能生成业务执行命令；
- 只有执行层能调用外部执行器；
- 执行层收到的必须是命令，不是 Agent 的自然语言建议；
- 核验 Agent 与执行 Agent 分离，避免“自己执行、自己验收”。

## 6. 共享工作区：多 Agent 的共同黑板

多 Agent 不能只通过自然语言互相转发摘要，必须围绕一份版本化共享工作区协作。

### 6.1 共享工作区的最小内容

```text
Workspace
- workspace_id
- goal_id
- topic
- version
- current_question
- constraints
- intel_items[]
- claims[]
- hypotheses[]
- agent_assessments[]
- general_assessment
- disagreements[]
- information_gaps[]
- options[]
- decision_status
- general_decision
- execution_order
- execution_report
- verification_result
- review
```

### 6.2 所有 Agent 产物必须带来源

每条材料至少包含：

```text
item_id
workspace_id
producer_agent
producer_role
created_at
input_item_ids
content
confidence
status: draft|shared|challenged|accepted|rejected|superseded
```

以下内容不得混在一起：

- 原始情报；
- Agent 对情报的解释；
- 将军补充的事实；
- 参谋的假设；
- 将军的最终决断；
- 执行器返回的观察；
- 核验后的业务结论。

### 6.3 共享工作区的写入规则

1. 原始情报只追加，不允许 Agent 覆盖；
2. Agent 只能修改自己创建的草案，不能静默修改其他 Agent 结论；
3. 将军修正必须保留原版本和修正来源；
4. 结论被质疑时标记 `challenged`，不能删除；
5. 事实升级为已验证状态必须有 Evidence；
6. 将军决断单独存储，不能被新的 Agent 分析覆盖；
7. 审计记录只追加。

## 7. 多 Agent 的协作流程

### 7.1 阶段一：目标对齐

```text
将军提出目标或问题
  ↓
ChiefAdvisor 复述目标、识别歧义、列出约束
  ↓
将军补充和修正
  ↓
形成 Goal Version 1
```

目标没有对齐前，专业 Agent 不得自行扩展任务范围。

### 7.2 阶段二：情报收集

```text
ChiefAdvisor 指定需要回答的问题
  ↓
ResearchAgent 按来源权限收集原始材料
  ↓
原始材料立即进入共享工作区
  ↓
将军可以查看、补充和指出遗漏
  ↓
AnalysisAgent 只基于工作区材料形成判断
```

情报阶段可以由 Agent 自动推进，但必须满足：

- 只访问已授权来源；
- 原始信息对将军可见；
- 不能将搜索摘要直接当作事实；
- 发现重大冲突立即上报。

### 7.3 阶段三：并行分析和反方审查

```text
AnalysisAgent：给出事实、假设、依据、置信度
RedTeamAgent：主动找反例、证据缺口和风险
FeasibilityAgent：评估资源、权限、成本和可执行性
        ↓
ChiefAdvisor 汇总一致项和分歧项
        ↓
将军查看，不要求接受多数意见
```

“多数 Agent 同意”只能作为参考信号，不能成为真理，也不能替代你的现场信息。

### 7.4 阶段四：方案协同

```text
OptionAgent 形成可行方案
  ↓
逐项比较目标收益、风险、成本、时效、可逆性
  ↓
RedTeamAgent 审查每个方案的失败路径
  ↓
ChiefAdvisor 给出推荐和不确定性
  ↓
将军采纳、修改、否决、暂缓或自提方案
```

方案数量按实际情况决定：

- 有明显不同路径时提供 2~3 个；
- 只有一条合理路径时说明原因，不凑假选项；
- 将军永远可以提出方案集之外的方案。

### 7.5 阶段五：决断和执行

```text
将军决断
  ↓
ChiefAdvisor 复述：目标、动作、范围、参数、停止条件
  ↓
将军确认命令
  ↓
Policy / Approval 校验
  ↓
ExecutionAgent 执行
  ↓
VerificationAgent 独立核验
  ↓
ChiefAdvisor 汇报给将军
```

执行中如果出现以下情况，必须暂停并请示：

- 命令参数不完整；
- 目标对象发生变化；
- 权限或风险等级升高；
- 结果未知；
- 出现命令未覆盖的新动作；
- 执行结果与预期不一致。

## 8. “多 Agent”与“多模型”不是一回事

第一阶段不要急着为每个 Agent 接不同模型。先把角色、输入、输出和权限跑通。

建议分三步：

### 阶段 A：单模型多角色

- 使用一个模型；
- 通过不同系统提示和结构化输出模拟多个岗位；
- 重点验证工作流和权限边界；
- 成本低，容易复现和测试。

### 阶段 B：按任务选择模型

- ResearchAgent 使用擅长检索和长上下文的模型；
- AnalysisAgent 使用擅长推理的模型；
- RedTeamAgent 使用不同提示或不同模型，减少同质化；
- VerificationAgent 尽量规则化，少依赖 LLM。

### 阶段 C：按风险和成本动态编排

- 低风险议题只启用情报 + 分析；
- 重要议题增加反方和可行性审查；
- 高风险议题必须增加独立核验和人工确认；
- 简单问题不启动完整参谋部，避免多 Agent 反而降低效率。

## 9. 安全边界：谁可以做什么

### 9.1 工具权限分层

```text
观察权限：读取已授权信息源
分析权限：读取共享工作区，写入判断草案
方案权限：读取共享工作区，写入方案草案
核验权限：读取执行记录和证据，写入验证结果
执行权限：只有执行 Agent，且必须持有有效 ExecutionOrder
决断权限：只有将军
```

### 9.2 Agent 默认不能拥有的能力

- 不允许专业 Agent 直接调用支付、发布、删除、权限修改等工具；
- 不允许通过自然语言向另一个 Agent 传递隐式执行命令；
- 不允许 Agent 自己提升风险等级或取消审批；
- 不允许 Agent 自己把 `hypothesis` 改成 `verified`；
- 不允许 Agent 自己结束目标；
- 不允许 Agent 通过“紧急”标签绕过将军决断。

### 9.3 L0~L5 与多 Agent 的关系

原 `03/04` 的风险等级继续有效：

- L0：只读观察和分析，可以自动并行；
- L1：本地草稿和内部整理，按命令范围执行；
- L2：可撤销内部动作，需明确命令和结果检查；
- L3：对外发布、共享数据修改，必须将军决断和确认；
- L4：账号、权限、凭据、支付等，强制人工参与；
- L5：删除、转账、不可逆动作，默认拒绝，不提供绕过开关。

多 Agent 只能提高分析覆盖面，不能降低动作风险等级。

## 10. 第一阶段开发重排

当前原目录里的 `core.py`、`autonomous_system.py`、`brain_modules/planner.py` 等都属于旧的 OpenClaw 自主循环参考实现。本轮不先在这些入口上堆多 Agent，也不直接让多 Agent 接管旧循环。

```text
Goal

GeneralDecision
ExecutionOrder

```

验收：

- 原始情报、假设和已验证事实不混淆；

### P1：单参谋离线协同

### P2：最小多 Agent 参谋部


- 原始情报只追加；

- 参谋长给你的是综合材料，不是替你拍板；
- Agent 数量增加后，仍只有你能生成最终决断。

### P3：方案、决断和命令

实现：

- 方案对比；
- 将军采纳/否决/修改/暂缓/自提；
- 决断历史；
- 命令复述和范围确认；
- Policy / Approval；
- 无命令不执行。

### P4：接入 SimulatorExecutor

把原 `06` 的 T01~T03 改造成参谋部验收，并扩展：

- T04：将军修正参谋假设；
- T05：将军否决推荐并自提方案；
- T06：多个 Agent 发现冲突证据，必须报告分歧；
- T07：执行超时，先观察后请示；
- T08：将军叫停，所有未完成执行停止；
- T09：核验 Agent 否定执行 Agent 的成功自报；

### P5：记忆、复盘和风格辅助

原有 Memory / MemoryV2 / VectorMemory 只能在边界清楚后接入：

- 将军明确确认的规则单独存；

- Agent 经验单独存；
- 原始情报和证据单独存；
- 参谋只能参考历史，不能用历史覆盖当前命令。

控制台重点不是展示一个“自动运行进度条”，而是展示：

- 各 Agent 判断；
- 分歧和风险；
- 方案对比；
- 将军决断；

- 执行汇报；

## 11. 赛马项目与规划工作区的边界

本工作区负责定义和维护熊猫智脑 Cola 方案的规划基线，开发目标是验证：

> **将军与参谋部能否共享信息、保留分歧、共同形成判断，并由将军控制执行。**

并行项目可以自行选择不同技术和产品表达；本工作区只基于已确认的产品需求和本目录基线，不为追赶任何一个实现而提前扩大范围。赛马只比较最终验收结果，不比较文件、代码或临时界面。

本目录的验收重点不是 Agent 数量，而是以下行为是否真实成立：

1. 你看见参谋使用的原始情报；
2. 你补充或修正后，参谋改变后续分析；
3. 不同 Agent 的意见可以不同并保留；
4. 参谋推荐不是你的决断；
5. 你可以否决、修改或自提方案；
6. 没有你的命令，任何 Agent 都不能执行外部动作；
7. 执行中出现意外，参谋回来报告；
8. 执行者和核验者相互独立；
9. 所有过程可以回放和追责。

## 12. 当前唯一开工指令

后续执行模型进入本目录后，按以下顺序工作：

1. 先读本文，再读原 `03`、`04`、`06`；
2. 不修改旧 `core.py`、`autonomous_system.py` 作为第一步；
3. 先实现 P0 共享工作区和协作对象；
4. 先用单参谋证明将军判断能改变流程，再引入最小四 Agent；
5. 任何 Agent 建议必须经过 `GeneralDecision` 才能变成 `ExecutionOrder`；
6. 任何真实外部执行前，必须通过 Policy、Approval 和独立验证；
7. 每个阶段都用离线测试证明权限边界，而不是只展示 Agent 输出文本；
8. 汇报时必须说明：共享材料、Agent 分工、将军决断、执行边界、测试结果和遗留风险。

**最终原则：多 Agent 是参谋部的组织形式；将军仍然是唯一的业务决断者。**

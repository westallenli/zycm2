## 1. 总体定位

熊猫智脑是你身边的一支参谋部，不是接收目标后自行统治和行动的自治系统。

它要解决的核心问题是：面对真实目标和不完整信息，如何让不同专业参谋有组织地完成情报、判断、反证、方案、可行性、执行和核验工作，并把真正需要你取舍的内容清楚地交还给你。

```text
你提出目标、约束和现场判断
        ↓
参谋长组织最小必要的专业协同
        ↓
共享证据、并行工作、受控汇合、保留分歧
        ↓
你形成或修正决断
        ↓
命令确认、策略校验、受控执行、独立核验
        ↓
共同复盘，形成可追溯的经验
```

唯一不变的权力边界：

```text
AdvisorProposal → GeneralDecision → ExecutionOrder → Policy / Approval → Executor
```

- `AdvisorProposal` 可以由一个或多个参谋形成；
- `GeneralDecision` 只能由将军形成；
- `ExecutionOrder` 必须是基于你的决断、范围明确的命令；
- `Policy / Approval` 只负责安全与授权，不替你做业务取舍；
- `Executor` 只执行命令并返回观察，不自行扩张任务。

`AdvisorProposal` 的对象边界：它不是新的独立文档类型，而是对“参谋侧建议载体”的统称——由 `DecisionBrief`（含推荐与分歧）、`OptionSet`（含前提与取舍）以及它们引用的 Evidence、Claim、Risk 对象组合而成，必须携带产生任务、产生岗位与工作区版本引用。09 号 P0 清单中的 OptionSet、GeneralAssessment 与 10 号的 DecisionBrief 在本文语境下都是 `AdvisorProposal` 的组成部分；它只能由参谋岗位或参谋长形成，永远不能由执行层或核验岗位产生。

## 2. 产品运行方式

熊猫智脑应有四种明确工作模式，而不是让系统始终处于“自动思考、自动推进”状态。

| 模式 | 适用情况 | 系统可自主做什么 | 必须交还给你什么 |
|---|---|---|---|
| 态势协作 | 收集信息、整理现状、低风险分析 | 按授权来源调研、归档证据、形成初步判断 | 关键冲突、信息缺口、你的补充机会 |
| 决策准备 | 多路径、风险或约束需要取舍 | 任务分派、方案比较、反方审查、可行性评估 | 方案、分歧、风险、推荐理由、需取舍项 |
| 命令执行 | 你已明确决定并确认命令 | Policy 校验、受控执行、状态观察 | 进度、异常、范围变化、独立核验结果 |
| 异常恢复 | 失败、结果未知、环境变化或叫停 | 暂停受影响工作、收集观察、评估回滚与影响 | 发生了什么、哪些命令失效、需要你重新决定什么 |

从模式转换必须可见、可回放。参谋长不得把“调研完成”自动解释成“你同意执行”。

### 3.1 将军协同界面

这是产品的主入口，不是 Agent 的运行日志面板。你应随时能看见：

- 当前目标、约束、成功标准和进度；
- 系统已经掌握的事实、仍在使用的假设、未知项和过期信息；
- 每项结论的来源、产生者和置信度；
- 参谋之间的分歧，以及分歧属于事实、预测还是价值取舍；
- 当前有哪些任务在进行、为什么进行、何时停止；
- 给你的 `DecisionBrief` 与需要你明确的具体问题；
- 已下达命令的范围、风险、审批、执行进度和核验结果；
- 你曾经的修正、否决和决断如何改变后续工作。

首版不应追求复杂对话式控制台。优先支持清晰的目标卡、共享态势、任务清单、证据链、方案对比和决断记录。

### 3.2 参谋部协调层

`ChiefAdvisor` 是系统中唯一的编排者。她不产生最终业务决断，而是维护目标推进的任务图：

```text
GoalFrame
  → QuestionTree
  → StaffPlan
  → StaffTask Graph
  → Rendezvous Gate
  → DecisionBrief / Next StaffPlan / Execution Draft
```

这一层负责：

- 把模糊目标澄清为本轮可回答的问题；
- 根据任务性质选择最小必要岗位；
- 定义任务输入、预期产出、依赖、预算、停止和升级条件；
- 控制哪些任务可并行、哪些任务必须等待证据；
- 在汇合门检查证据质量、遗漏、冲突和任务完成度；
- 把参谋产物转成你能审阅、能修正的决策材料；
- 在你的决断后，起草命令并监督执行和核验的交接。

参谋长不直接调用高风险工具，不对真实目标做价值判断，也不把“多数参谋同意”当成推进依据。

### 3.3 专业参谋能力层

岗位不是常驻全开，而是由任务图按需启用。

| 岗位 | 不可替代的责任 | 主要输入 | 主要输出 | 不拥有的权力 |
|---|---|---|---|---|
| ResearchAgent | 取得、定位并标注原始材料 | 调研任务、授权来源 | Evidence、来源质量、信息缺口 | 不能把摘要升级为事实 |
| AnalysisAgent | 将材料组织为解释、假设和情景 | Evidence、约束 | Claim、Hypothesis、置信度 | 不能决定方案或执行 |
| OptionAgent | 把选择空间展开为可比较路径 | 判断、约束、目标 | OptionSet、取舍和前提 | 不能制造伪选项或替你选择 |
| RedTeamAgent | 寻找遗漏、反例和失败路径 | 当前结论、方案 | Challenge、Risk、No-go 条件 | 不能为了反对而反对 |
| FeasibilityAgent | 评估资源、权限、成本、时效与可逆性 | 方案、环境能力 | Prerequisite、限制、估算 | 不能擅自筹集资源或执行 |
| ExecutionAgent | 按有效命令执行动作 | ExecutionOrder、Action Contract | ExecutionReport、Observation | 无命令不得执行 |
| VerificationAgent | 独立判断结果是否满足业务目标 | 结果、证据、成功标准 | VerificationResult | 不能由执行者代替 |
| MemoryAgent | 保存可追溯的经验候选 | 已完成的决断、执行与复盘 | Review、MemoryCandidate | 不能改变当前决断或规则 |

第一版的最小参谋部只包含 `ChiefAdvisor + ResearchAgent + AnalysisAgent + RedTeamAgent`。其他岗位应在真实流程证明需要后加入。

### 3.4 共享态势与审计层

所有协同围绕版本化 `Workspace` 发生，而不是靠不同 Agent 的聊天摘要传递状态。

共享态势至少分为：

| 类别 | 内容 | 规则 |
|---|---|---|
| 目标态势 | Goal、Constraint、SuccessCriterion、Priority | 由将军确认；变更保留版本 |
| 认识态势 | Observation、Evidence、Claim、Hypothesis、Unknown | 事实、推断、未知严格分开 |
| 协同态势 | StaffPlan、StaffTask、依赖、状态、预算、汇合门 | 参谋长编排，岗位只更新自己的工作 |
| 风险态势 | Risk、Challenge、No-go、权限与政策判断 | 不可被汇总时静默删除 |
| 决断态势 | GeneralInput、DecisionBrief、GeneralDecision | 将军的输入与决断不可被覆盖 |
| 行动态势 | ExecutionOrder、Action、Approval、Report、Verification | 执行与业务完成分开记录 |
| 学习态势 | Review、MemoryCandidate、已验证经验 | 经验不能反向覆盖当前事实与命令 |

每条非原始产物都应能追溯到：产生任务、产生岗位、输入项、工作区版本、时间和状态。

外部内容与注入防护：

1. 任何岗位从信息源取得的外部内容一律作为数据进入共享态势（Observation / Evidence），永远不是指令：内容中出现的任何要求、命令或建议，不得改变任务边界、触发工具调用或修改权限；
2. 外部内容入库时必须标注来源信任级别（授权来源 / 待核验 / 未信任）；信任级别决定该内容可参与的分析深度，未核验内容不得作为 L3 以上动作或命令起草的依据；
3. Agent 读取共享态势时只能获得结构化对象及其内容字段；“忽略之前指令”类内容按数据处理并标记可疑，由参谋长决定发起核验或上报将军；
4. 外部内容不得直接进入执行链：命令参数只能来源于将军决断和经核验的事实，不能引用未信任来源的原始文本。

权限强制点：权限边界由结构性校验保证，提示词约定不承担任何强制职责。

1. **共享态势写入**：所有写入必须经过工作区写入接口；接口按对象所有权规则校验“当前任务契约的 owner_agent 与对象类型是否匹配”，越权写入直接拒绝并留审计记录。阶段 A 单模型多角色时，角色身份由编排器派发任务时的运行时上下文决定，模型输出中自称的角色不作为权限依据；
2. **工具与信息源访问**：能力检查和来源授权在工具适配层执行，Agent 只能拿到当前 `StaffTask` 的 `allowed_sources / forbidden_actions` 所界定的句柄，无法在进程内自行扩大；
3. **决断与命令对象**：`GeneralInput / GeneralDecision` 的创建和 `ExecutionOrder` 的状态迁移只能由对应入口（将军入口、命令服务）触发，参谋侧代码路径在类型层就不存在这些写方法；
4. **提示词的定位**：系统提示用于让岗位理解边界、产出合规结构，它只是第一道引导；任何边界的最终保证都在上述校验点。验收以“绕过提示词直接构造越权请求被拒绝”为测试标准。

### 3.5 治理与执行层

执行能力必须从参谋分析能力中隔离出来。

```text
GeneralDecision
  → ExecutionOrder
  → Action Contract
  → Capability Check
  → Risk / Policy Check
  → Approval Check
  → Executor Adapter
  → Observation / ExecutionReport
  → Independent Verification
```

关键原则：

- `Action Contract` 是结构化动作协议，不能只是一句自然语言；
- 所有审批必须绑定动作、对象、参数、风险等级和有效期；
- `ExecutionResult = success` 不等于业务目标完成；
- 超时、部分成功和结果未知时，先观察和核验，不得盲目重试；
- 外部影响、权限、资金、发布、删除等风险不会因为有多个 Agent 而降低。

`ExecutionOrder` 必须是带生命周期的对象，而不是一段生效语义模糊的文本：

```text
draft           参谋长依据 GeneralDecision 起草，不是命令，不可执行
pending_confirm 已提交将军确认
confirmed       将军已确认，进入 Policy / Approval 校验
active          校验通过，执行中（可 paused）
completed / failed / cancelled / expired / superseded    终态
```

命令生命周期规则：

1. 只有 `confirmed` 及之后状态的命令才可能进入执行链；`draft` 不是命令；
2. 参谋长起草（draft）与将军确认（confirmed）是两个不同状态，任何实现不得让起草动作直接产生可执行命令；
3. 同一目标的新命令被确认时，必须原子地将旧的 `active` 命令置为 `superseded`，作废动作与审计记录在同一事务内完成；
4. `cancelled / expired / superseded` 是终态，不可复活；恢复执行必须基于新命令；
5. 从 `paused` 恢复前，必须复检命令有效期与关联审批有效期，任一过期即转请示，不得直接续跑。

决断归属与身份边界：

1. `GeneralInput`、`GeneralDecision`、命令确认和 Approval 必须携带归属字段（`decided_by / confirmed_by / approver`）；归属值必须来自经过认证的将军入口，不能是 Agent 自报的字符串；
2. 包括参谋长在内的任何参谋岗位，都无权写入上述归属字段，也不能代替将军会话产生决断、确认或审批对象；
3. 首版安全前提显式声明为：单用户、本地运行、单一将军入口；本文全部权力边界都以该前提为条件；
4. 在接入任何第二类输入来源（远程 API、多账号、外部自动触发）之前，必须先实现入口认证与归属校验；未实现前系统应拒绝进入命令执行模式并显式报错，而不是默认信任。

## 4. 核心协同闭环

### 4.1 决策准备闭环

```text
将军提出目标或问题
  ↓
参谋长复述目标、列出歧义与约束
  ↓
将军确认或修正目标框架
  ↓
参谋长建立问题树与最小 StaffPlan
  ↓
专业参谋按 StaffTask 工作并写入共享态势
  ↓
参谋长在汇合门检查证据、依赖和冲突
  ↓
不足：补查 / 重排任务 / 向将军请示
足够：形成 DecisionBrief
  ↓
将军采纳、修改、否决、暂缓、要求补查或自提方案
```

### 4.2 执行与验证闭环

```text
GeneralDecision
  ↓
参谋长复述目标、范围、参数、风险、停止条件和验收标准
  ↓
将军确认 ExecutionOrder
  ↓
Policy / Approval 校验
  ↓
ExecutionAgent 执行
  ↓
VerificationAgent 独立核验
  ↓
完成：向将军汇报并进入复盘
异常：暂停受影响动作，形成 GeneralQuestion
```

### 4.3 你介入后如何影响系统

你的任何修正都不是普通聊天信息，而是具有下游影响的 `GeneralInput`。参谋长必须识别受影响范围：

| 你的输入 | 必须失效或重审的内容 |
|---|---|
| 修改目标或成功标准 | 当前问题树、所有未完成任务、方案与命令草案 |
| 新增约束或风险偏好 | 方案比较、可行性、风险审查和预算 |
| 否决推荐路径 | 相关 Option、依赖任务和执行草案 |
| 补充事实 | 依赖该事实的 Claim、预测和方案判断 |
| 暂停或取消命令 | 未启动的动作、重试计划、后续执行任务 |
| 接受某项风险 | 对应 No-go 条件、审批说明和执行范围 |

这保证“你在考虑，系统也在考虑”不是两个平行频道，而是真正共同维护同一份态势。

认定门槛：不是你的每句话都是 `GeneralInput`。系统必须区分三类输入：

1. **随口讨论**：不改变任何对象，只进入对话记录；
2. **澄清问答**：只补充解释现有对象，不触发下游失效；
3. **正式修正**：升级为 `GeneralInput`，按上表触发下游失效与重审。

判定有歧义时，参谋长必须先复述她理解的影响范围并请你确认，确认后该输入才升级为 `GeneralInput`；不得静默升级，也不得静默忽略。未升级的内容进入澄清记录，不改变任务图。

## 5. 关键协调规则

### 5.1 最小必要编制

参谋长每次必须说明启用理由、未启用理由、预期贡献和停止条件。默认组合：

| 工作场景 | 建议编制 |
|---|---|
| 明确、低风险事实查询 | Research；必要时 Verification |
| 有材料但需解释局势 | Research + Analysis |
| 需要比较可逆方案 | Analysis + Option |
| 高影响、难回滚或外部影响决策 | Research + Analysis + Option + RedTeam + Feasibility |
| 已确认命令的执行 | Execution + Verification |
| 执行异常或结果未知 | ChiefAdvisor + Verification，再按事实缺口增派岗位 |

### 5.2 并行与串行

可并行的条件：输出不互相依赖、不写同一对象、不争用同一受限资源、失败互不阻断且可独立回收。

必须串行的条件：后续判断依赖证据、动作需要前置审批、同一方案对象需要统一版本、风险评估必须看到完整方案。

第一版采用简单、可解释的规则任务图。不要先建设自治调度器、消息队列或复杂的多 Agent 对话协议。

### 5.3 汇合门与停止条件

每一阶段都需要明确的汇合门：

| 汇合门 | 主要判断 | 可能结果 |
|---|---|---|
| `evidence_ready` | 证据是否足够、冲突是否显式 | 分析、补查或向你说明不足 |
| `analysis_ready` | 事实、推断、假设是否分离 | 方案设计或反方审查 |
| `options_ready` | 路径是否真实可比、前提是否完整 | 可行性和风险审查 |
| `decision_ready` | 剩余问题是否属于你的取舍 | 形成 DecisionBrief |
| `execution_ready` | 已有决断且命令是否完整 | 命令确认与策略检查 |
| `verification_ready` | 是否满足业务成功标准 | 汇报完成、复盘或异常升级 |

停止条件同时防止两种失败：过早给出伪确定结论，以及无止境收集信息却不向你提出真正的取舍。

### 5.4 分歧处理

| 分歧 | 正确处理 | 禁止处理 |
|---|---|---|
| 事实不一致 | 回到来源、观察和独立核验 | 用平均数或多数票处理 |
| 假设不同 | 标明条件，做最小验证或情景推演 | 把假设伪装成已知事实 |
| 预测不同 | 展示影响、概率区间与关键先验 | 强迫形成单一预测 |
| 价值权衡不同 | 清楚交给将军决定 | 让参谋长替你加权 |
| 任务边界冲突 | 重写 StaffTask 和依赖 | 让多个岗位持续重复劳动 |

### 5.5 何时向将军请示

必须请示的情形包括：目标或成功标准歧义、证据不足且继续成本显著、出现不可消除的价值取舍、风险等级上升、命令范围外的新动作、关键结论冲突、预算耗尽仍无法判断、执行结果异常或未知。

请示必须是一个结构化问题：已知什么、未知什么、影响什么、有哪些选择、需要你决定哪一项。

等待与超时：

1. 每项 `GeneralQuestion` 携带建议答复期限；到期未答复时，参谋长只能催办一次并说明逾期影响，不得替你作任何业务决定；
2. 等待期间保持安全默认：受影响任务保持暂停、不启动新的依赖任务、已到停止条件的任务停止并记录；等待期间到达的新证据只入库，不触发结论更新；
3. 你恢复处理时，参谋长先复述等待期间积累的变化（新证据、过期材料、失效任务），再继续原问题或按你的新指示重排。

## 6. 技术与部署策略

### 6.1 第一阶段采用模块化单体

建议先建设一个本地可运行、可测试、可回放的模块化单体：

- 一个确定的领域模型与持久化边界；
- 一个参谋长编排模块；
- 多个实现同一岗位契约的 Agent 适配器；
- 一个模拟执行器与策略层；
- 一个简单的协同界面或本地控制面；
- 一套离线场景测试。

理由：当前最大风险是协同逻辑和权力边界是否真实成立，不是吞吐量或跨机器部署能力。微服务、消息队列、自治队列和多进程调度会过早引入状态一致性、重试和可观测性复杂度。

### 6.2 存储与审计原则

首版应优先支持事务性状态、对象版本和追加式审计：

- 核心状态与关系使用关系型持久化；
- 原始证据、执行日志和大型附件以引用方式关联；
- 决断、审批、执行和核验记录只追加、不静默覆盖；
- 用关联 ID 串起 Goal、Workspace、StaffTask、Evidence、Decision、Order 与 Execution；
- 记忆检索只能辅助后续分析，不能写回为当前事实；
- 审计事件采用链式哈希：每条记录包含前一条审计事件的摘要，系统提供一键校验链条完整性的能力，任何篡改都会断链并被发现；
- 共享态势对象的写入携带版本号（revision）做乐观并发控制：并行任务基于过期版本提交产物时更新被拒绝，必须重读最新版本后重新提交，禁止静默覆盖他人产物；
- 原始证据以不可变快照保存并记录内容哈希，后续任何结论引用证据时可验证其内容未被改动。

### 6.3 模型策略

首版优先验证“单模型、多岗位契约、结构化产物”的流程。后续只有在测得研究质量、反方独立性、成本或速度存在问题时，才按岗位选择不同模型。

模型数量不是参谋质量指标。证据链、任务边界、独立核验和你对决断的控制权才是。

### 6.4 非功能要求

| 维度 | 首版要求 | 设计含义 |
|---|---|---|
| 决断完整性 | 没有 `GeneralDecision` 不得创建有效执行命令 | 将军权力边界必须由对象与流程共同保证 |
| 身份归属 | 决断、确认与审批绑定经认证的将军入口；首版显式声明单用户本地前提 | 未实现入口认证前不接受第二类输入来源 |
| 可追溯性 | 每个结论、命令和结果可回溯到任务、输入、产生者和版本 | 不以聊天摘要作为唯一记录 |
| 可恢复性 | 暂停、中断、超时和结果未知后可恢复并避免重复副作用 | 状态、审批和幂等信息必须持久化 |
| 可复现性 | P0~P4 使用固定离线案例可重复验收 | 不把随机模型输出或外部网络当测试基准 |
| 成本与时效 | 每项 StaffTask 有预算、停止条件和升级条件 | 防止全员并行和无限调研 |
| 安全与权限 | 工具按能力与风险分层，审批绑定具体动作；权限由结构校验强制，提示词不作保证 | 多 Agent 不得成为绕过安全的通道 |
| 可观测性 | 可看见任务状态、依赖、汇合门、阻塞原因和异常 | 参谋长的编排不能成为黑箱 |
| 演进性 | 岗位与执行器通过稳定契约接入 | 先模块化单体，后续按问题拆分，不预设分布式系统 |

### 6.5 关键架构决策记录

#### ADR-11-01：首版采用模块化单体与离线场景驱动验收

- 决策：协同状态、任务编排、参谋岗位、策略层和模拟执行器先运行在同一可测试系统内。
- 原因：当前风险集中在协同语义、权限边界和将军介入，而不是横向扩展。
- 代价：未来多工作区或高并发时可能需要拆分；在出现真实容量或隔离需求前不提前引入消息队列与分布式状态一致性。

#### ADR-11-02：共享 Workspace 是协同状态的唯一事实来源

- 决策：Agent 间的自然语言转述不能替代版本化对象；所有可影响下游的材料必须写入 Workspace。
- 原因：避免状态漂移、证据丢失、少数意见被覆盖和将军修正失效。
- 代价：需要定义对象所有权、版本和引用关系；这是首版必须承担的复杂度。

#### ADR-11-03：参谋长以任务图和汇合门协调，而非以自由对话协调

- 决策：`StaffTask`、依赖、预算、停止条件和汇合门是主协调协议；对话只承担解释与协商呈现。
- 原因：可审计、可测试，并能控制并行度和责任边界。
- 代价：探索性工作需要显式创建新任务，不能无限自由扩散。

#### ADR-11-04：执行与核验必须独立，且排在参谋协同闭环之后

- 决策：只由持有效命令的执行层调用工具，核验由独立岗位基于成功标准进行。
- 原因：防止建议越权、执行者自证成功和失败后盲目重试。
- 代价：流程多出一次核验交接；对低风险任务可简化核验深度，但不得取消结果记录。

#### ADR-11-05：权限边界采用结构性强制，提示词约定仅作辅助

- 决策：对象所有权、工具授权、命令状态迁移的强制点分别放在工作区写入接口、工具适配层和命令服务的类型与流程约束上；提示词只负责引导岗位行为，不作为任何边界的保证手段。
- 原因：单模型多角色阶段，模型自报身份不可信；只有校验点位于代码路径上，“无命令不执行”“岗位不越权”才能被离线测试断言。
- 代价：写入接口、适配层和命令服务必须实现为唯一通道且不可绕过；灵活性下降——新增岗位或工具必须先扩展契约与授权配置，不能靠改提示词临时放开。

### 6.6 确定性与工程诚实纪律

以下纪律适用于所有阶段的验收，机制来源见[多智能体决策改造系统调研笔记](<D:/熊猫开发项目/熊猫智脑cola v4/docs/research/多智能体决策改造系统调研笔记_V1.0.md>)：

1. **确定性优先**：核验、评分、一致性检查、汇合门判断等能用确定性规则实现的，优先实现为确定性工具；LLM 只承担规则无法覆盖的解释与判断，其输出不得替代可计算的检查；
2. **缺失显式标注**：输入分量缺失时显式标记 `unavailable` 并说明对结论的影响，禁止用默认值填充或编造补齐；
3. **能力不可用显式报错**：依赖未配置、数据未就绪或能力未接入时，相关流程必须返回明确错误或 `not_ready` 状态并说明缺什么；禁止用模拟输出冒充真实能力，也不用模拟评测结果宣称具备生产能力。

## 7. 分阶段落地路线

### 阶段 P0：协同地基

目标：先让系统有可追溯的共同语言。

范围：

- Goal、Constraint、SuccessCriterion、Workspace；
- Evidence、Claim、Hypothesis、Risk、Option；
- StaffPlan、StaffTask、状态、依赖与版本；
- GeneralInput、GeneralDecision、ExecutionOrder；
- 产物来源、对象所有权、追加式审计规则。

验收：

- 事实、推断、未知、风险和你的输入能够并列保存；
- 任一结论能回溯产生任务、输入和岗位；
- 你的修正能被记录为明确版本，不被参谋产物覆盖；
- 不引入真实工具、网络或执行。

不做：LLM 自主循环、真实执行器、长期记忆、复杂 UI。

### 阶段 P1：单参谋协同闭环

目标：证明参谋长能服务你的判断，而不是替你推进。

范围：

- `ChiefAdvisor` 基于规则建立 GoalFrame 和 QuestionTree；
- 生成最小 `StaffPlan` 与 `StaffTask`；
- 使用离线固定材料形成第一份 `DecisionBrief`；
- 支持你采纳、修改、否决、暂缓和要求补查；
- 你的输入使下游草案失效并重新编排。

验收：同一案例中，你修改一个约束后，后续问题、方案和建议发生可解释变化；没有你的 `GeneralDecision` 时，系统只能停留在建议阶段。

### 阶段 P2：最小专业参谋部

目标：验证专业分工与受控汇合，而非增加 Agent 数量。

范围：

- `ResearchAgent`、`AnalysisAgent`、`RedTeamAgent`；
- 任务依赖、并行条件、汇合门和停止条件；
- Evidence Pack、Claim、Challenge 的独立写入；
- 事实冲突、假设冲突和少数意见的保留。

验收：

- 两个互不依赖的调研任务可并行；依赖证据的分析不会抢跑；
- RedTeam 的挑战不会被参谋长摘要抹掉；
- 证据不足时不能生成伪确定的建议；
- 参谋长能说明每个岗位为何被启用或未启用；
- 对照验收：同一目标分别以“仅参谋长”与“最小三岗位”各运行一次，三岗位版本必须检出至少一项单参谋版本遗漏的反例、风险或证据缺口，并记录双方成本；若对照连续无净增益，进入 P3 前必须重估编制必要性。

### 阶段 P3：方案与决断质量

目标：让参谋部把“信息”转成你可以真正取舍的材料。

范围：

- `OptionAgent` 与 `FeasibilityAgent`；
- OptionSet、前提、成本、时间、可逆性与 No-go 条件；
- `DecisionBrief` 的固定结构；
- `GeneralDecision` 的版本、范围和风险接受记录；
- 价值取舍、证据不足和关键分歧的请示机制。

验收：将军可否决所有推荐并自提方案；系统能够据此重排下游任务，而不是强行回到原有推荐。

### 阶段 P4：受控执行与独立核验

目标：证明命令边界和工程闭环，而不是追求真实自动化。

范围：

- `ExecutionOrder`、Action Contract、Policy、Approval；
- `ExecutionAgent`、`VerificationAgent`；
- `SimulatorExecutor` 和固定模拟世界；
- 成功、失败、超时、部分成功、权限不足、结果未知、暂停恢复。

验收：

- 无命令或命令过期时拒绝执行；
- L3 以上动作在未审批时不得调用执行器；
- 执行成功但业务结果未达成时，不得标记完成；
- 执行异常会暂停、形成 GeneralQuestion，而不是自行改变战略。

### 阶段 P5：复盘与受控记忆

目标：让系统从可验证经验中改进协同，而不是累积不可控的“印象”。

范围：

- Review、MemoryCandidate、经验适用边界；
- 决断、执行、核验的完整回放；
- 相似失败和有效做法的检索；
- 对参谋编排质量的反馈，例如重复调研、漏掉反方、过早请示或过度工作。

验收：相似历史会被检索并影响下一轮建议，但系统不会把过去经验当作当前事实，也不会覆盖你的新命令。

### 阶段 P6：真实低风险能力与控制面

目标：在已验证边界内逐步连接真实环境。

范围：

- 本地安全读写与可撤销操作；
- 受控 API 或内部测试环境；
- 人工执行器；
- 展示共享态势、任务图、证据、决断、执行和回放的控制面。

验收：外部动作全链路可追溯、可暂停、可核验；执行器可替换，业务决断和协同状态不依赖具体工具。

### 阶段 P7：按需扩展能力

仅在前述阶段已稳定后评估：

- 多模型岗位选择；
- 蒸馏人物/流派视角作为一次性分析插件；
- 浏览器执行器；
- 更复杂的任务图优化；
- 多工作区、长期目标和多人协作。

每项扩展必须证明它解决了已观测到的质量、成本、速度或覆盖问题，不能因为“看起来更智能”加入。

## 8. 全程验收主线

无论处于哪个阶段，都以以下十项作为整体架构的验收标准：

1. 你能看到参谋使用的原始情报及其来源；
2. 你补充或修正后，参谋的后续任务和判断会改变；
3. Agent 分工按任务需要产生，不是固定全员运行；
4. 不同意见可见且保留，不被多数或汇总掩盖；
5. 参谋长能说明为什么此时要继续、停止、并行或请示；
6. 参谋推荐与将军决断有严格对象边界；
7. 无有效命令时，任何 Agent 都无法改变外部现实；
8. 执行者与核验者独立，执行成功不等于业务完成；
9. 异常会暂停并向你说明需要决定什么；
10. 从目标到复盘的材料均可追溯和回放。

## 9. 主要风险与控制

| 风险 | 表现 | 控制方式 |
|---|---|---|
| 编排过度自治 | 参谋长绕过你推进重大取舍 | GeneralQuestion 和 GeneralDecision 作为硬门槛 |
| 多 Agent 重复劳动 | 多人搜索同一材料、互相覆盖 | StaffTask、来源范围、依赖和对象所有权 |
| 虚假共识 | 多个岗位复制同一推断 | 独立初判、RedTeam、分歧对象与证据回溯 |
| 无限调研或反复推演 | 成本升高、长期不形成材料 | 预算、停止条件、汇合门与请示机制 |
| 上下文与版本漂移 | 新信息未影响旧结论 | Workspace 版本、输入引用和下游失效规则 |
| 执行越权 | 建议被当成命令、工具被滥用 | Decision / Order 分离、Policy、Approval、能力检查 |
| 自证成功 | 执行者将返回值当作完成 | 独立 Verification 与业务成功标准 |
| 记忆污染 | 未验证经验反向影响事实 | MemoryCandidate、来源、适用域和人工确认 |
| 过度工程 | 先建分布式集群、复杂 UI 或多模型 | 模块化单体、离线验收、按观察到的问题扩展 |

## 10. 当前开工边界

后续实施应严格遵守：

1. 先实现 P0 的对象、溯源、版本与权限边界；
2. 先用一个离线案例证明 P1 的“将军修正能改变协同”；
3. 再引入最小三岗位专业参谋部，验证 P2 的分工、依赖和分歧；
4. 执行器只从 P4 的模拟器开始；
5. 不把人物圆桌、多模型、浏览器执行器、长期记忆或分布式基础设施塞进首版；
6. 每阶段只有通过对应验收，才进入下一阶段；
7. 任何实现都不得削弱将军的目标权、取舍权、命令权和结果接受权。

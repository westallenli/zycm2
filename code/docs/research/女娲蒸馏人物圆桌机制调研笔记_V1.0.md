# 女娲蒸馏人物圆桌机制研究与熊猫智脑适配规格 V1.0

> 适用工作区：[熊猫智脑cola v4](<D:/熊猫开发项目/熊猫智脑cola v4>)
>
> 本文研究两个已安装技能并将其适配到熊猫智脑：
>
> - 女娲 `huashu-nuwa`：从一手资料蒸馏人物的心智模型、决策启发式、反模式、内在张力与诚实边界；
> - `ljg-roundtable`：让不同思想代表围绕定义、分歧和更深问题进行结构化圆桌讨论。
>
> 结论：**应当吸收，但不能原样照搬。** 熊猫智脑应实现“智囊圆桌”，让经女娲蒸馏的思维视角成为参谋部的可选成员；圆桌的工作是扩大和校正将军的判断空间，决断权始终属于将军。

---

## 1. 吸收后的定位

熊猫智脑中的多 Agent 有两种根本不同的成员，不能混为一谈：

| 类型 | 是什么 | 解决什么 | 能否执行 |
|---|---|---|---|
| 专业 Agent | 有明确岗位职责的工作者，如情报、核验、执行 | 收集、验证、编排和执行工作 | 只有 ExecutionAgent 在持有效命令时可以 |
| Perspective（思维视角） | 由女娲蒸馏的人物或流派认知框架 | 提供不同判断镜片、反方挑战与取舍视角 | **不能执行，默认没有工具权限** |

`PerspectiveCouncil`（智囊圆桌）不是一群人格化 Agent 自由闲聊，而是一个**受证据约束、有限轮次、由将军决断的高价值讨论机制**。

```text
已验证情报 + 将军问题
        ↓
参谋长选择适合的思维视角
        ↓
智囊圆桌：独立判断 → 交叉质询 → 结构化分歧
        ↓
参谋长形成决策材料（不是替将军拍板）
        ↓
将军：采纳 / 修改 / 否决 / 自提方案 / 补查信息 / 暂缓
        ↓
GeneralDecision → ExecutionOrder → Policy → 执行
```

圆桌位于“共同讨论”阶段，绝不跨入“命令确认”或“执行”阶段。

## 2. 从女娲吸收的精华

### 2.1 蒸馏的是思维系统，不是口吻

女娲的关键原则是“捕捉 HOW they think，不是 WHAT they said”。一个可参与圆桌的视角，必须至少包括：

- 3~7 个有跨场景证据的心智模型；
- 5~10 条带适用条件的决策启发式；
- 反模式：这个视角明确拒绝什么；
- 内在张力：它在哪些价值之间会冲突；
- 能力边界与失效条件；
- 调研截止日期和来源强度。

熊猫智脑不应把“模仿某人的讲话风格”当成核心能力。表达风格可作为 UI 中的可选呈现层，但会议后台首先要保存**结构化的判断和依据**。

### 2.2 证据、来源、矛盾和局限必须随视角入场

女娲的有效设计是：一手资料优先，区分“本人说过”“他人评价”“框架推断”，发现矛盾不能和稀泥，信息不足时扩大诚实边界。

对应到熊猫智脑，每个 `PerspectiveProfile` 必须版本化：

```text
perspective_id
name
profile_version
research_cutoff_at
source_summary
primary_source_ratio
mental_models[]
heuristics[]
antipatterns[]
internal_tensions[]
domain_strengths[]
domain_blind_spots[]
honesty_boundaries[]
refresh_policy
```

参会时，每个判断必须标记为以下之一：

| 类型 | 含义 | 能否当作事实 |
|---|---|---|
| `evidence_claim` | 由本次共享证据支持的事实判断 | 只有引用 Evidence ID 后才可进入验证流程 |
| `source_grounded_view` | 该人物在公开资料中确有相近观点 | 不能替代本次事实 |
| `framework_inference` | 按蒸馏模型推导出的观点 | 不能伪装成该人物原话，更不能当已验证事实 |
| `value_preference` | 对风险、速度、可逆性等取舍的偏好 | 由将军决定是否采用 |
| `unknown` | 缺资料或超出能力圈 | 必须显式保留，不能用流畅表达掩盖 |

### 2.3 女娲式“先研究再发言”应保留

女娲为每个视角定义了与该视角匹配的研究路径。例如芒格看激励与最大风险，Karpathy 看代码、数据和部署可靠性。

适配规则：

- 当前事件的事实调研由 `ResearchAgent` **先统一完成并写入共享工作区**；
- 圆桌成员默认只读取同一份版本化证据包，避免每个视角各搜一遍、产生事实漂移和重复成本；
- 某个视角需要的关键事实缺失时，只能提出 `ResearchRequest`，不能凭角色设定补造；
- 参谋长决定是否补查；补查后开启新一轮，不在旧材料上悄悄改结论。

## 3. 从圆桌技能吸收的精华

`ljg-roundtable` 的核心价值不是“让名人逐个讲话”，而是以下五项：

1. **按议题选人，而不是固定专家名单**：每位成员必须补一个不可替代的变量；
2. **先统一定义**：许多分歧不是结论冲突，而是概念、时间尺度或成功标准不同；
3. **形成张力网络，而不是简单正反方**：高价值讨论需要不同假设与权衡相互碰撞；
4. **动态发言而不是轮流表演**：下一位发言者必须回应某项具体主张；
5. **主持人展示分歧结构而不制造伪共识**：产出争议地图、证据缺口和下一层问题。

这些原则可以直接成为熊猫智脑的会议协议。

## 4. 不能原样照搬的部分

| 原圆桌做法 | 为什么不适合熊猫智脑 | 熊猫智脑改法 |
|---|---|---|
| 真实人物 + MBTI 介绍 | MBTI 与业务判断无关，容易让讨论变成角色表演 | 用思维模型、适用范围、盲区、来源质量介绍参会视角 |
| 主持人作为“判官” | 将军才是业务决断者；不同价值取舍没有统一判官 | `CouncilFacilitator` 只管理证据、分歧和会议流程 |
| 自由多轮讨论直到用户喊停 | 成本和上下文不可控，容易发散 | 默认 1 次独立陈述 + 1 次定向交叉质询，最多 2 轮 |
| 每位人物凭既有知识发言 | 容易过时或虚构最新事实 | 事实问题先读取共享 Evidence Pack，缺口显式请求补查 |
| 完整逐字长文本作为主要产物 | 可回放但检索、比较和执行困难 | 同时保存原文记录和结构化 Argument Map / Decision Brief |
| 讨论后给“可执行建议” | 容易跨过将军决断直接进入行动 | 只生成建议和方案；必须由将军形成 `GeneralDecision` |
| “至少一个意外人物” | 为猎奇加入无关视角会增加噪声 | 只有能补关键变量时才引入跨域视角 |

## 5. 智囊圆桌的启动门槛

圆桌不是每个问题的默认流程。它适用于：

- 目标重要、影响范围大或难以回滚；
- 可行方案之间存在真实取舍；
- 证据足够，但解释和策略存在分歧；
- 将军主动要求“多视角推演”；
- 当前判断正在被单一模型、单一专业或单一偏好支配；
- 已经出现一次重大失败，需要从不同框架复盘。

以下情况不启动圆桌：

- 纯事实查询；
- 规则明确、低风险的例行处理；
- 证据严重不足，应该先补查；
- 将军已经给出明确且完整的执行命令；
- 只是为了“多 Agent 看起来更高级”。

```text
能否用一条已验证规则处理？ → 能：不召开
证据是否足够支撑讨论？     → 否：先调研
存在重大取舍或解释冲突？     → 否：普通参谋建议
将军要求多视角或议题高影响？ → 是：召开智囊圆桌
```

## 6. 参会视角的动态选择

### 6.1 不是常驻固定班子

每次会议由 `ChiefAdvisor` 提议 2~4 个视角，并说明：

```text
本轮问题：...
需要检验的关键变量：...
视角 A 的独特贡献：...
视角 B 的独特贡献：...
A 与 B 的预期张力：...
不邀请 C 的原因：当前问题不需要其能力 / 已过期 / 与其他视角高度重复
```

将军可以确认、替换、删除或额外邀请视角。对重大议题，邀请名单本身也应成为一次可见的协同选择。

### 6.2 选择标准

每个候选视角要经过五个检查：

1. **领域相关性**：其心智模型能否解释当前问题的一部分？
2. **变量独特性**：移除它后，会缺少哪个关键变量？
3. **张力价值**：它是否会挑战现有主假设，而非重复共识？
4. **证据适配性**：现有 Evidence Pack 是否足以支撑它的分析？
5. **新鲜度和边界**：其资料是否过期或超出能力圈？

### 6.3 一个产品决策的示例

议题：“是否在本季度为熊猫智脑接入浏览器执行能力？”

可能选择：

| 视角 | 独特变量 | 可能挑战 |
|---|---|---|
| Karpathy 式工程现实主义 | demo 与真实可靠性的差距、尾部失败 | “能演示”不代表能稳定运行 |
| 芒格式逆向与激励分析 | 最大失败路径、错误激励和不可逆风险 | “功能更强”不等于收益大于事故成本 |
| Jobs 式产品聚焦 | 用户真实体验、克制、端到端体验 | “多工具”可能损害产品的清晰度 |
| 将军本人 | 现场约束、目标优先级、风险承受 | 外部视角没有的真实上下文 |

这不是让这些人物替将军投票，而是把不同问题拆开摆到桌面上。

## 7. 智囊圆桌会议协议

### 7.1 会前：建立统一底稿

`CouncilBrief` 必须由参谋长创建，所有成员读取同一版本：

```text
council_id
goal_id
topic
question_to_decide
why_now
success_criteria
constraints
current_options
known_facts[]          # 带 Evidence ID
known_assumptions[]
unknowns[]
previous_decisions[]
general_assessment
risk_context
workspace_version
```

事实、假设、价值偏好、预测必须明确分开。证据不足的问题先回到调研，不用圆桌假装解决。

### 7.2 第一段：定义与独立立场

主持人先提出三个对齐问题：

1. 我们到底要决定什么，不决定什么？
2. 成功如何衡量，时间尺度多长？
3. 本轮最关键的约束和不可接受后果是什么？

随后各视角在**不读取其他成员结论**的情况下并行提交 `PerspectivePosition`：

```text
position_id
perspective_id
claim
claim_type
supporting_evidence_ids
framework_used
confidence
key_assumption
strongest_counterargument
information_needed
recommended_option_or_boundary
```

先独立后互看，是为了减少第一个发言者锚定其他成员，避免虚假共识。

### 7.3 第二段：定向交叉质询

`CouncilFacilitator` 不要求人人回应所有人，只挑 1~3 条决定性冲突：

```text
质询对象：Perspective A
需要回应：Perspective B 的主张 #...
质询问题：你反对的事实、假设或价值取舍具体是什么？
可选回答：同意 / 不同意 / 需要补证 / 超出边界
必须输出：理由 + 证据 ID 或 framework_inference 标记
```

有效的交锋必须指向：

- 同一事实的不同解释；
- 相互冲突的假设；
- 不同的价值权重；
- 不同的时间尺度；
- 对某方案最大风险的不同判断。

禁止只重复立场、泛泛反驳或用角色口吻掩盖没有依据的断言。

### 7.4 第三段：主持人生成争议地图

主持人只做四件事：

1. 标出确定事实、待验证假设和价值偏好；
2. 标出一致项和不可消除的分歧；
3. 指出哪一项新证据最可能改变决断；
4. 将讨论压缩为将军可以选择的方案与边界。

标准产物是 `CouncilSynthesis`：

```text
consensus_points[]
disagreements[]
evidence_gaps[]
assumption_tests[]
option_comparison[]
facilitator_recommendation  # 可为空，永远不是决定
no_go_conditions[]
questions_for_general[]
```

可以在 UI 里展示论证图、因果图或二维权衡图，但图必须表达结构，不能装饰性复述发言。

### 7.5 第四段：将军决断

会议在出现以下任一种事件后结束：

- 将军选择、修改、否决或自提方案；
- 将军要求补查某个证据缺口；
- 将军决定暂缓；
- 默认两轮上限已到，仍无足够材料。

会议的输出只能是 `DecisionBrief`，不能直接创建 `ExecutionOrder`：

```text
CouncilSynthesis
  → GeneralDecision（将军显式产生）
  → ExecutionOrder（命令确认后生成）
  → Policy / Approval
  → ExecutionAgent
```

## 8. 会议参与者的诚实契约

每个 Perspective 在会议中必须遵守：

1. 不把框架推断伪装成某人物的原话；
2. 不把旧资料当作当前事实；
3. 不能用“角色性格”代替证据；
4. 超出能力圈时必须说 `unknown` 或提出调研请求；
5. 发现新事实与蒸馏结论冲突时，事实优先，标记该视角待刷新；
6. 只能提出建议、反对或问题，不能下达命令；
7. 不对将军的决断投票，也不以多数意见制造压力。

人物名称在产品中应显示为“某某视角”或“某某框架”，并附简短来源说明。系统不声称真的在让历史人物本人发言。

## 9. 会议记录、记忆与回放

应同时保存两层内容：

| 层 | 保存内容 | 用途 |
|---|---|---|
| 原始会议记录 | CouncilBrief、每个立场、质询、主持人总结、将军输入 | 审计、复盘、检查是否篡改分歧 |
| 结构化决策记录 | 事实、假设、冲突、方案、将军决断、结果、复盘 | 搜索、风格学习、后续相似问题辅助 |

不可压缩或覆盖的内容：原始证据引用、将军决断、被否决方案、关键分歧和执行命令。

可以形成经验记忆的内容：哪些视角在何类问题上补到了盲区、哪些假设常常错误、哪些证据缺口最终改变了决断。

系统必须避免把“某个视角常被将军采纳”学习成“以后该视角自动替将军拍板”。历史只改变参谋的排序和说明，不改变你的当前权力。

## 10. 与现有多 Agent 基线的关系

[09_熊猫智脑将军参谋与多Agent协作重新对齐基线_V1.0.md](<D:/熊猫开发项目/熊猫智脑cola v4/docs/09_熊猫智脑将军参谋与多Agent协作重新对齐基线_V1.0.md>) 中的分层保持不变：

```text
ResearchAgent        负责事实与证据
AnalysisAgent        负责常规形势分析
RedTeamAgent         负责一般反方审查
ChiefAdvisor         负责协作编排
PerspectiveCouncil   负责特定重要问题的多框架深度讨论
ExecutionAgent       只执行将军的有效命令
VerificationAgent    独立核验结果
```

`PerspectiveCouncil` 不是替代 `RedTeamAgent`，也不是每次都开。它用于普通岗位分析无法消化的重大取舍与世界观冲突。

## 11. 开发顺序调整

在原 P0~P6 基础上增加一个受控阶段：

```text
P0  协作对象和共享工作区
P1  单参谋离线协同
P2  最小专业参谋部（Research / Analysis / RedTeam / ChiefAdvisor）
P2.5 智囊圆桌（PerspectiveProfile + Council 协议）
P3  方案、将军决断和命令边界
P4  SimulatorExecutor、结果验证和异常请示
P5  决策历史、记忆和蒸馏视角刷新
P6  真实执行器与协同控制台
```

P2.5 的第一版不需要真的蒸馏新人物。可先使用 2~3 个由固定结构化规则表示的视角，验证协议、记录和权限边界；随后再接入女娲生成的 `PerspectiveProfile`。

## 13. P2.5 验收场景

| 编号 | 场景 | 必须证明 |
|---|---|---|
| R01 | 选人 | 每个视角都有独特变量、张力理由和能力边界，不能为了凑人数入场 |
| R02 | 证据共享 | 所有本次事实引用同一 Evidence Pack；缺资料只能发起 ResearchRequest |
| R03 | 独立初判 | 成员先独立立场后交叉阅读，保留不同意见 |
| R04 | 诚实边界 | 无来源的新观点标为 `framework_inference`，不能伪装成真人原话或事实 |
| R05 | 交叉质询 | 质询指向具体主张、假设或价值取舍，不允许泛泛辩论 |
| R06 | 分歧保留 | 主持人不能用多数意见消除分歧，必须明确哪些问题由将军取舍 |
| R07 | 将军改写 | 将军否决、修改或自提方案后，形成新决断版本，会议推荐保持历史可见 |
| R08 | 权限隔离 | 任一视角和主持人都不能直接生成 ExecutionOrder 或调用工具 |
| R09 | 时效冲突 | 新事实与某视角旧资料冲突时，新事实优先且视角标记待刷新 |
| R10 | 回放 | 能回放证据、独立立场、质询、争议地图、将军决断和最终结果 |

## 14. 最终结论

女娲与圆桌机制可以成为熊猫智脑的明显差异点：不是“多个模型回答同一个问题”，而是把经过证据蒸馏的不同思维框架组织成一次**可追溯、有张力、可被将军随时介入的参谋会议**。

但系统必须坚持四条底线：

1. 人物视角是认知工具，不是假装真人；
2. 当前事实必须来自共享证据，不来自人物设定；
3. 会议追求把分歧和权衡摆清楚，不追求投票形成共识；
4. 圆桌输出建议，只有将军决断才能进入执行链。

# 「多智能体决策改造」系统调研笔记 V1.0

> 调研对象：`D:/熊猫开发项目/多智能体决策改造/docs/多智能体架构与使用指南.md`（洪水预警多智能体系统，四层架构：前端窗口 / 常驻监控 Agent / NAT LLM 编排 / MCP 工具 / 确定性决策数据层）
>
> 结论：**决策数据层的工程机制值得直接吸收进熊猫智脑规格；其多 Agent 组织方式（常驻循环 + ReAct 自主编排）不能照搬。**

---

## 1. 值得吸收的机制（映射到 Cola 规格）

| 对方机制 | 吸收方式 | 补哪个缺口 |
|---|---|---|
| Decision 状态机 `draft → pending_review → approved/rejected → superseded` | 作为 `ExecutionOrder` 生命周期设计的现成参照：draft（参谋长起草）→ pending_confirm（待将军确认）→ confirmed/expired/cancelled/superseded | 评审疑点①②（命令无状态机、起草≠生效矛盾） |
| 审计事件 SHA-256 链式哈希（含 `previous_hash`）+ 一键验链端点 | 把 11 号"追加式审计"升级为防篡改审计链；回放可信度有了技术保证 | 强化 NFR 可追溯性；支撑 C04/R10 回放验收 |
| 所有写操作带 `revision` 乐观锁，旧版本更新抛冲突（API 409） | `Workspace` 并发写入的落地机制：并行任务产物按版本回收，冲突显式报错而非静默覆盖 | 评审疑点⑧（并行汇合确定性） |
| Evidence 不可变快照 + `content_hash` | 具体化 09 号"原始情报只追加"规则 | 认识态势对象细化 |
| 确定性评分工具：分量分解、缺失分量显式标 `unavailable` 不编造、结果声明 `is_official_warning: false` | VerificationAgent 尽量规则化的具体范式；"缺什么就说什么"是诚实边界的工程化表达 | P0~P4 可复现验收；诚实契约 |
| 没有 key 时端点明确报错、"不会假装工作"；库空时报 `bootstrap_required` | 写入阶段验收纪律：能力不可用时显式降级声明，禁止用模拟输出冒充真实能力 | 05 号"不用模拟评测结果宣称具备生产能力"的延续 |
| 能力可用性矩阵（现在能玩 vs 需要 key） | 每阶段交付时附"已验证 / 未接入"清单 | 阶段汇报格式 |
| MCP 工具服务器作为工具适配层；约束写在工具层 docstring（不对外发布警报、归一化单位） | 印证 Policy 约束应落在工具/执行层结构上，而不是依赖提示词自觉 | 权限强制点（评审补充发现） |

## 2. 不能照搬的部分

| 对方做法 | 为什么不适合熊猫智脑 |
|---|---|
| ReAct 循环（思考→调工具→观察→再思考，10 轮迭代）作为 LLM 编排主体 | 这正是 09 号排除的旧 `Think→Decide→Act→Observe` 自主闭环。ReAct 只能作为**单个 StaffTask 内部**的受控实现细节，不能成为岗位间协调协议 |
| 多 Agent = 4 个常驻监控循环（`check_interval` 定时跑） | 与"最小必要编制、任务图驱动"直接冲突。常驻全开正是我们要避免的成本噪声源。唯一可保留形态：态势协作模式下规则型定时采集（L0 只读、只写 Observation、可见可停），且必须由 StaffPlan 显式授权 |
| `created_by` / `approver` 是自报字符串 | 没有解决身份问题，反而印证评审疑点④：行业通行做法就是自报。熊猫智脑的 `GeneralDecision.decided_by` 必须另行设计，不能照抄 |
| 单案例线性生命周期 `open → reviewing → decided → closed` | 只适合一次性研判；熊猫智脑需要目标→问题树→任务图→决断→执行→核验的长链路，案例模型只能作局部参照 |

## 3. 对方系统反向验证的判断

1. 它没有分歧保留机制、没有反方岗位、没有汇合门、没有将军/参谋权责分离——评估可以被 `supersede` 但少数意见无处安放。这正是熊猫智脑方案的差异点，不是需要追赶的差距。
2. 它的审批由 API 调用者完成，与"参谋长起草、将军确认"的分离无关——说明权力边界设计无法从通用决策系统里白拿，必须自己写硬。

## 4. 落地建议（待用户批准后执行）

1. 在 11 号或新文档中为 `ExecutionOrder` 定义状态机，参照对方 Decision 状态机扩展；
2. 将审计链哈希、revision 乐观锁写入 11 号 §6.2 存储与审计原则；
3. 将"确定性优先、缺失显式标注、能力不可用显式报错"写入阶段验收纪律；
4. 不修改 09/10 的角色与编排设计。

## 5. 追补（2026-08-22）：对照《系统设计逻辑总结》的二次吸收

来源：`D:\熊猫开发项目\多智能体决策改造\docs\系统设计逻辑总结.md`。此前第 2 节所列四项机制已全部在 P0~P4 实现并验收；本次对照新增结论：

### 已落地并经本次对照验证的

- 审计链旁路纪律：原项目要求"写审计必须走唯一入口，旁路写入即毁公信力"。熊猫智脑已将事件列表封为只读元组，唯一写入口 `append_event`（结构强制，非约定）；
- 确定性优先、缺失显式 unavailable、不冒充官方：已体现为条件式推荐、insufficient_evidence 请示项、`is_official` 语义由信任级别承担。

### 新增可吸收（按阶段归位）

1. **单位白名单 + 时区归一**（字段名携带单位、白名单外直接拒、统一时区 validator）→ P6 数据接入时采用；
2. **ValidationReport 逐条报错不静默丢弃** → P6 批量摄取通道设计；
3. **摄取侧幂等导入** → P6（与执行侧幂等键同一纪律的数据面版本）；
4. **bootstrap_required 显式空态**（绝不生成样例数据）→ P6 真实数据模式纪律；
5. **LLM 可插拔可缺席**（provider 工厂 + 无 key 规则兜底 + prompt 禁令）→ P7 引入 LLM 岗位时的架构前提：现有规则层即兑底层，LLM 只能是增强层；
6. **领域材料配置化**（审核过的 YAML，不造地理数据）→ playbook 领域内容外置为审核配置的演进方向；
7. **SQLite + revision 锁**的取舍表 → P6 持久化选型参考（与单用户本地前提吻合）。

### 维持不采纳

- 常驻 asyncio 监控循环、NAT/ReAct 编排主体、React 前端层（远期控制面板另行评估）。
